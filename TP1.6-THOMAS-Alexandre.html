§9 Exigences transverses

Ce document constitue les sections §9 et §10 de la DCT SupEvents. Il transforme la DCT d'un document descriptif en un document auditable : l'analyse STRIDE couvre les deux flux financiers critiques de la plateforme, les SLO chiffrés définissent les engagements de performance, et la matrice de traçabilité permet à tout auditeur de vérifier la couverture complète des 21 exigences du CDC.

§9.1 — Sécurité (analyse STRIDE)

L'analyse STRIDE est appliquée aux deux flux les plus critiques du système : le flux d'inscription payante (cœur du modèle économique) et le flux de réception webhook Stripe (point d'entrée des confirmations de paiement). Ces deux flux ont été retenus car ils sont techniquement distincts — l'un implique une session utilisateur interactive, l'autre un appel serveur-à-serveur non authentifié par session — et couvrent ensemble la quasi-totalité des vecteurs d'attaque financiers de la plateforme.

§9.1.1 — Flux 1 : Inscription payante

Flux 1

Inscription payante

EventModule · TicketModule · PaymentModule · Stripe · RabbitMQ
Diagramme de séquence
U : Utilisateur
FE : Frontend (SPA)
EM : EventModule
TM : TicketModule
PM : PaymentModule
ST : Stripe
RMQ : RabbitMQ
DB : PostgreSQL
  1. U→FE : Clic « S'inscrire » sur fiche événement
  2. FE→EM : GET /events/{id} — vérification disponibilité
  3. EM→DB : SELECT places_restantes WHERE event_id = {id}
  4. EM→FE : 200 OK { disponible: true, prix: 15.00 }
  5. FE→TM : POST /tickets { eventId, userId } JWT Bearer TM crée une réservation temporaire en base (TTL 10 min) via SELECT FOR UPDATE
  6. TM→PM : POST /payments { ticketId, montant: 1500 } service token
  7. PM→ST : POST /v1/payment_intents { amount, currency, metadata }
  8. ST→PM→FE : { clientSecret, paymentIntentId }
  9. FE→ST : Stripe.js confirmCardPayment(clientSecret) — 3DS si requis Direct FE→Stripe, coordonnées bancaires jamais côté serveur
  10. FE→PM : POST /payments/{paymentIntentId}/confirm JWT Bearer
  11. PM→ST : GET /v1/payment_intents/{id} — re-vérification serveur-to-Stripe Double vérification : le montant et le statut sont confirmés côté Stripe avant toute écriture en base
  12. PM→DB : UPDATE payments SET status = CAPTURED
  13. PM→RMQ : publish(payment.captured, { ticketId, userId, eventId })
  14. RMQ→TM : consume(payment.captured)
  15. TM→DB : UPDATE tickets SET status = CONFIRMED → Email de confirmation SendGrid

Description du flux

L'utilisateur, préalablement authentifié (JWT valide), clique sur « S'inscrire » : le frontend interroge l'EventModule pour vérifier la disponibilité en temps réel, puis le TicketModule crée immédiatement une réservation temporaire en base avec un TTL de 10 minutes — ceci protège contre la sur-vente en conditions de concurrence (SELECT FOR UPDATE). Le PaymentModule délègue ensuite la création du PaymentIntent à Stripe et renvoie le clientSecret au frontend ; à aucun moment les coordonnées bancaires ne transitent par nos serveurs (conformité PCI-DSS niveau 4). Le navigateur appelle directement Stripe.js pour la saisie de la carte et la confirmation 3DS si requise. Une fois le paiement confirmé côté client, le frontend notifie notre PaymentModule qui re-vérifie l'état du PaymentIntent côté Stripe avant de mettre à jour la base et de publier l'événement payment.captured dans RabbitMQ. Le TicketModule consomme cet événement et confirme définitivement le ticket, déclenchant l'envoi de l'email de confirmation. Ce découplage par message garantit que la confirmation n'est émise que si le paiement est effectivement capturé.

Tableau STRIDE

Menace Risque identifié Mesure de défense retenue
S
Spoofing		 Un attaquant usurpe l'identité d'un utilisateur légitime pour acheter un ticket à sa place, en rejouant un JWT volé via une connexion non-TLS. Tous les endpoints API requièrent un JWT signé RS256 avec expiration 15 min. Le refresh token est stocké en cookie HttpOnly SameSite=Strict, inaccessible au JavaScript. TLS 1.3 obligatoire sur tous les appels ; HSTS max-age=31536000.
T
Tampering		 Un attaquant intercepte et modifie le montant du PaymentIntent en transit (ex. passer de 1500 à 1) pour payer moins. Le clientSecret Stripe est lié au montant fixé serveur-side lors de la création ; toute modification côté client est rejetée par Stripe. Re-vérification serveur-to-Stripe (GET /v1/payment_intents/{id}) avant toute mise à jour en base.
R
Repudiation		 Un utilisateur conteste avoir initié l'inscription ou le paiement, rendant difficile la preuve de l'action. Chaque étape est journalisée avec horodatage, userId, ticketId et paymentIntentId dans la table audit_events (insertion append-only via trigger PostgreSQL). Le paymentIntentId Stripe constitue une preuve externe indépendante.
I
Information Disclosure		 Les données de carte bancaire de l'utilisateur sont exposées dans les logs applicatifs ou dans les réponses API. Coordonnées bancaires traitées uniquement par Stripe.js, jamais par nos serveurs. Middleware de sanitisation masquant cvv, cardNumber, clientSecret dans tous les logs stdout. Colonne stripe_customer_id chiffrée en base (AES-256 via pgcrypto).
D
Denial of Service		 Un attaquant déclenche en masse des créations de tickets PENDING pour épuiser les places disponibles et bloquer les inscriptions légitimes. TTL 10 min sur tickets PENDING — libération automatique si paiement non finalisé. Rate-limiter (Nginx + Redis) : 5 tentatives/utilisateur/événement par 60 secondes. Réservation via SELECT FOR UPDATE dans une transaction PostgreSQL pour éviter la sur-vente.
E
Elevation of Privilege		 Le service TicketModule utilise un token lui permettant d'accéder aux endpoints d'administration de PaymentModule (remboursements, annulations globales). Service tokens à portée restreinte (OAuth 2.0 scope payment:create uniquement pour TicketModule). Endpoints d'admin (/payments/refund) nécessitent le scope payment:admin, attribué exclusivement aux identités ops via le provider OIDC interne.

§9.1.2 — Flux 2 : Réception webhook Stripe

⚠️
Point d'attention conceptuel critique Ce flux est fondamentalement différent du flux d'inscription : il n'y a aucune session utilisateur, aucun JWT. L'authenticité de la requête est établie uniquement par une signature HMAC-SHA256 (en-tête Stripe-Signature). Écrire « Auth JWT » comme mesure de défense serait une erreur conceptuelle.
Flux 2

Réception webhook Stripe

PaymentModule · RabbitMQ · PostgreSQL
Diagramme de séquence
ST : Stripe (externe)
GW : API Gateway (Nginx)
PM : PaymentModule
DB : PostgreSQL
RMQ : RabbitMQ
TM : TicketModule
  1. ST→GW : POST /webhooks/stripe type: "payment_intent.succeeded"
  2. GW : Vérification IP allowlist Stripe (plages officielles) avant forward Si IP non Stripe → 403 Forbidden, aucun log détaillé (pas d'oracle)
  3. GW→PM : Forward complet avec header Stripe-Signature
  4. PM : Vérification signature HMAC-SHA256 sur le payload brut (avant tout parsing JSON) avec STRIPE_WEBHOOK_SECRET Si signature invalide → 400 Bad Request sans détail
  5. PM→DB : SELECT * FROM payments WHERE stripe_payment_intent_id = {id}
  6. Idempotence : si paiement déjà CAPTURED → 200 OK sans action (prévention du rejeu)
  7. PM→DB : BEGIN TRANSACTION → UPDATE payments SET status = CAPTURED + INSERT INTO audit_events
  8. PM→RMQ : publish(payment.captured, { paymentIntentId, ticketId, userId }) Publication dans la même transaction → cohérence garantie (ou les deux réussissent, ou aucune)
  9. RMQ→TM : consume(payment.captured) → UPDATE tickets SET status = CONFIRMED
  10. PM→ST : 200 OK

Description du flux

Stripe envoie un POST HTTP sur notre endpoint /webhooks/stripe dès qu'un PaymentIntent change d'état. Ce flux n'implique aucune session utilisateur : l'authenticité est établie par une signature HMAC-SHA256 incluse dans l'en-tête Stripe-Signature. La première défense est une allowlist IP Nginx filtrée sur les plages officielles Stripe. Le PaymentModule recalcule la signature HMAC sur le payload brut (avant tout parsing JSON) — utiliser req.body parsé serait un bug de sécurité documenté. L'idempotence est garantie par une vérification en base avant toute mise à jour : si le paiement est déjà CAPTURED, on retourne 200 sans rejouer l'action. La mise à jour en base et la publication dans RabbitMQ sont réalisées dans la même transaction PostgreSQL pour garantir la cohérence.

Tableau STRIDE

Menace Risque identifié Mesure de défense retenue
S
Spoofing		 Un attaquant forge une requête POST sur /webhooks/stripe en imitant Stripe pour déclencher une confirmation de paiement sans paiement réel. Vérification obligatoire de la signature HMAC-SHA256 via stripe.webhooks.constructEvent(rawBody, sigHeader, secret). En complément : allowlist IP sur les plages officielles Stripe. Toute requête sans signature valide → 400 sans log détaillé (pas d'oracle).
T
Tampering		 Un attaquant intercepte le webhook en transit et modifie le montant ou le paymentIntentId pour créditer un autre ticket. La signature HMAC-SHA256 est calculée sur le payload brut : toute modification d'un seul octet invalide la signature. Le corps de la requête est passé à constructEvent avant tout parsing JSON — il est impossible de modifier le payload sans invalider la signature.
R
Repudiation		 Stripe conteste avoir envoyé un webhook, ou notre système ne peut pas prouver qu'un événement a bien été traité à un moment donné. Chaque webhook reçu est loggué en base (webhook_events : id, type, payload_hash, timestamp, status) avant tout traitement. Le paymentIntentId Stripe est vérifiable via l'API Stripe dashboard. Logs append-only (trigger PostgreSQL).
I
Information Disclosure		 Le payload du webhook contient des informations sensibles (email, montant, détails de carte partielle) loggués en clair dans les fichiers de log. Seuls le type, le paymentIntentId et un hash du payload apparaissent dans les logs stdout. Le payload complet est stocké en base chiffré (AES-256). Niveau DEBUG désactivé en production. Logs rotatifs conservés 90 jours dans un stockage chiffré à accès restreint.
D
Denial of Service		 Un attaquant connaissant l'URL du webhook envoie des milliers de requêtes par seconde pour saturer le PaymentModule. Rate-limiter dédié sur /webhooks/stripe : 60 req/min par IP (429 + Retry-After). La vérification HMAC est réalisée avant tout accès en base, limitant le coût des requêtes invalides. Autoscaling horizontal PaymentModule (min 2, max 6 pods) + circuit breaker sur RabbitMQ.
E
Elevation of Privilege		 L'endpoint webhook est accessible sans authentification ; un attaquant l'utilise pour déclencher des transitions d'état non autorisées (ex. passer un paiement directement en REFUNDED). Liste blanche de types d'événements acceptés (payment_intent.succeeded, payment_intent.payment_failed, charge.refunded). Machine d'état en code (PENDING→CAPTURED→REFUNDED uniquement) — impossible de court-circuiter les transitions.

§9.2 — Performance

Les trois exigences ci-dessous sont des SLO (Service Level Objectives) dérivés des exigences ENF 01 et ENF 02 du CDC SupEvents. Chaque fiche précise l'objectif mesurable avec percentile, la solution technique avec les mécanismes nommés, les composants impactés et la méthode de vérification avec outils et seuils d'alerte.

PERF-01

Latence des endpoints critiques — Catalogue & Inscription

ENF 01
Objectif mesurable
🎯 p95 ≤ 500 ms
Sur les endpoints GET /events (catalogue paginé), GET /events/{id} (fiche événement), POST /tickets (création de réservation). Mesuré en conditions de charge nominale : 200 utilisateurs simultanés, fenêtre glissante de 5 minutes, excluant le temps de réponse de Stripe (appel externe non maîtrisé).
Solution technique
  1. Cache Redis sur GET /events et GET /events/{id} — TTL 60 s, invalidation sur mutation via événement event.updated
  2. Index PostgreSQL composite (status, date, category) sur la table events pour les requêtes de filtrage catalogue
  3. Index PostgreSQL (event_id, status) sur la table tickets pour le comptage de places restantes
  4. Pagination curseur (keyset pagination) pour éviter les OFFSET coûteux au-delà de la page 3
  5. Pool de connexions PgBouncer (mode transaction, pool_size=20 par instance) pour éviter la saturation des connexions PostgreSQL
Composants impactés EventModule §7.1 TicketModule §7.3 Redis (cache) PostgreSQL
Méthode de vérification Outil : k6 (load-test-catalogue.js versionné dans le dépôt)
Fréquence : CI automatique à chaque merge sur main + cron k6 Cloud toutes les 6h en production
Seuils d'alerte : WARNING p95 > 400 ms CRITICAL p95 > 500 ms sur 5 minutes consécutives → PagerDuty
Dashboard Grafana + Prometheus pour visualisation temps réel
PERF-02

Disponibilité mensuelle de la plateforme

ENF 02
Objectif mesurable
🎯 Disponibilité ≥ 99,5 %
Sur l'ensemble des endpoints publics (catalogue, inscription, authentification), mesurée par monitoring externe (Uptime Robot) avec sonde toutes les 60 secondes depuis 3 régions géographiques.
SLO cible 99,5 %
Budget d'erreur mensuel (30 jours) 3h 36 min = 0,5% × 43 200 min = 216 minutes
Calcul 43 200 min/mois × 0,005 = 216 min = 3h36
Ce budget est partagé entre déploiements planifiés et incidents.
Solution technique
  1. Déploiement blue-green sur Kubernetes — mises à jour sans coupure de service
  2. Réplication PostgreSQL en streaming (1 primaire + 1 réplica read) avec bascule automatique Patroni (failover < 30 s)
  3. Redis Sentinel (3 nœuds) — bascule automatique en cas de défaillance du nœud primaire
  4. RabbitMQ en cluster (3 nœuds, mirrored queues) — élimination du SPOF sur le bus de messages
  5. Health checks Kubernetes (liveness + readiness probes) avec restart automatique des pods défaillants
Composants impactés Tous les modules §7.1–§7.7 PostgreSQL Redis RabbitMQ Kubernetes
Méthode de vérification Outil : Uptime Robot (monitoring externe, sondes HTTPS depuis EU-West, EU-Central, US-East, toutes les 60 s)
Fréquence : continue, en permanence
Seuils d'alerte : Slack + PagerDuty si indisponibilité > 5 minutes consécutives
Gouvernance : Si budget consommé à > 80% avant le 25 du mois → gel des déploiements non-urgents jusqu'au mois suivant
PERF-03

Capacité à absorber un pic d'inscriptions concurrentes

ENF 01 — 500 utilisateurs simultanés
Objectif mesurable
🎯 500 inscriptions simultanées
Sans dépasser p95 ≤ 800 ms, sans erreur 5xx et zéro sur-vente (tickets confirmés > capacité), dans une fenêtre de 60 secondes représentant un pic d'ouverture des inscriptions pour un événement populaire.
Solution technique
  1. Transaction PostgreSQL avec SELECT FOR UPDATE SKIP LOCKED pour la gestion concurrente sans deadlock
  2. Autoscaling horizontal du TicketModule (HPA Kubernetes : scale-out si CPU > 60% ou file RabbitMQ > 100 messages, min 2 / max 8 pods)
  3. File RabbitMQ avec prefetch=10 pour lisser la charge et éviter la surcharge du TicketModule
  4. Circuit breaker (Resilience4j) sur les appels PaymentModule → Stripe avec fallback (mise en file de la confirmation) si timeout Stripe > 3 s
  5. Jeton de réservation temporaire (TTL 10 min) pour éviter la sur-vente en cas d'abandon de paiement
Composants impactés TicketModule §7.3 PaymentModule §7.4 PostgreSQL RabbitMQ Kubernetes HPA
Méthode de vérification Outil : k6 (stress-test-inscription.js) — 500 VU en rampe de 10 secondes, profil complet (GET /events/{id} → POST /tickets → confirmation)
Fréquence : mensuelle en staging (pré-production isolée)
Critères de succès : p95 < 800 ms, error_rate < 0,1%, zéro sur-vente vérifiée par comptage post-test
Alerte production : si taux d'erreur sur /tickets > 1% sur 2 minutes → autoscaling immédiat + notification ops

b) Mécanismes de protection transverses

  • Chiffrement TLS 1.3 en transit — périmètre : toutes les communications (client-API, API-API, API-PostgreSQL, API-Redis). Certificats renouvellés automatiquement via Let's Encrypt (cert-manager). HSTS max-age=31536000, includeSubDomains.
  • Chiffrement de la base de données au repos — périmètre : volume PostgreSQL chiffré LUKS (AES-256 niveau disque). Colonnes sensibles (stripe_customer_id, refresh_token_hash) chiffrées au niveau applicatif via pgcrypto (AES-256 GCM), clés gérées par HashiCorp Vault.
  • Hashage des refresh tokens — périmètre : table users, colonne refresh_token_hash. Seul le SHA-256 du token est stocké — en cas de compromission de la base, les tokens ne peuvent pas être utilisés.
  • Gestion des secrets via HashiCorp Vault — périmètre : toute l'infrastructure. Aucun secret en clair dans les manifests Kubernetes. Injection via Vault Agent Sidecar. Rotation automatique trimestrielle.
  • Séparation stricte des environnements — périmètre : dev / staging / production entièrement distincts. Jeux de données de dev synthétiques (Faker.js). Données de production jamais copiées en développement.
  • Audit log inviolable — périmètre : toutes les actions sensibles (connexion, inscription, paiement, modification de profil, exercice de droits RGPD). Table audit_events en append-only (trigger bloquant UPDATE/DELETE). Export vers S3 immuable (Object Lock COMPLIANCE) toutes les heures.
  • Minimisation des données dans les logs — périmètre : tous les microservices. Middleware de sanitisation masquant email, cardNumber, cvv, token, clientSecret. Classification RBAC des logs (PUBLIC / INTERNAL / RESTRICTED).

§10 Matrice de traçabilité

La présente matrice croise l'intégralité des 21 exigences du CDC SupEvents — 13 exigences fonctionnelles (EF 01 à EF 13) et 8 exigences non-fonctionnelles (ENF 01 à ENF 08) — avec les éléments de la DCT produits lors des TP 1.1 à 1.6. Une exigence est couverte si au moins un module de §7 ou une section de DCT en documente la conception. Les zones non couvertes sont signalées explicitement avec leur traitement prévu. L'objectif est qu'un auditeur externe puisse, en 30 minutes, vérifier que toutes les exigences du CDC sont traitées dans la documentation.
